# 研究报告 05：Agent 主循环与工具系统

> 对标对象：ZCode v3.17.1 `apps/zcode-cli/packages/core/src/{runtime,tool,compact,subagent}`、`contracts/src/tools/contract.ts`、`adapters/src/storage/session-store/`
> 调研日期：2026-11-01 · 用途：CB 主循环（src/agent-core/loop.ts）与工具契约演进参考

---

## 0. TL;DR

ZCode 主循环的四条关键不变量（原文总结）：
1. **所有进入模型历史的东西必须先持久化成功**（先落库再提交内存）；
2. **入参归一化只做一次**，确认窗/hook/权限规则/handler 读同一份字节；
3. **事件是唯一事实源，UI 是投影**，崩溃后从 message/part 行重建；
4. **一切排队**（用户输入、通知、控制轮）共享一个优先级队列（now/next/later）。

CB 的主循环机械层面已与 ZCode 同构（重试/三层压缩/doom-loop/收尾轮/中断全有），结构性差距集中在：工具结果单轨 string、无结构化错误、无 command queue 优先级、子代理轨迹不落库。

## 2. 主循环：一轮 turn 的生命周期

核心文件：`runtime/agent-runtime.ts`（839 行，类体只持字段，方法全经 mixin 挂上）+ `runtime/methods/turn.ts`（1179 行）+ `turn-loop.ts` + `turn-model-step.ts`（944 行）+ `agent/turn-machine.ts`（状态机 `TurnPhase: idle→processing_input→awaiting_model_response→streaming→scheduling_tools→executing_tools→aggregating_results→completing/error`，白名单转移）。

流程（每段有 `startTurnPhase/completeTurnPhase` 计时打点）：
1. **排队**：prompt 包成 `PromptRuntimeCommand`（priority "next"）进 runtime command queue；
2. **准备**：`createTurnModel`（失败走 creationFallback 降级链，**仍保留已接纳输入**）→ 上下文重建 → session hooks → 持久化 → TurnStarted 事件；
3. **循环**（`runRegularTurnLoop`）：新输入时机才消费通知 → MCP 刷新 → 工具面投影（按 mode/plan/disallowlist）→ system-reminder 附件注入（固定顺序）→ **microcompact → autoCompact** → provider 请求（cache-control 在投影后统一设置）→ `runModelBackedTurnStep` → 工具执行结算 → 返回 continue/break/output_continuation；
4. **收尾**：TurnComplete（usage/cacheStats）→ turnNumber++ → 投影重建。

**中断**：用户 Stop → abort 当前 foreground controller；被取消的工具统一改写为 `"The user doesn't want to proceed with this tool use..."`（`USER_STOPPED_TOOL_RESULT_CONTENT`）；成功收尾前写 `[Request interrupted by user]` 标记（source=interrupt_marker，持久化，冷恢复按 source 重放）；**取消时的流式快照也会持久化**。

> CB 对照：CB 的 loop.ts 已有同构流程（drain 通知→压缩→buildAPIMessages→runModelTurn→工具执行）。可抄细节：`creationFallback` 保留已接纳输入、interrupt marker 持久化、TurnPhase 计时打点。

## 3. Command Queue：一切排队

**六种命令**共享一个队列（`RuntimeCommandPriority = "now"|"next"|"later"`）：

| mode | 内容 | 优先级 |
|---|---|---|
| prompt | 用户消息 | next |
| target-continuation/-loop | goal 自动续跑 | next/later |
| task-notification | 后台任务完成通知 | later |
| subagent-message | 子代理回话 | later |
| control-only-turn | GUI 配置修订的记录轮 | later |

关键机制：
- `dequeueNextBatch()` 把**同优先级同 offPeakExecutionId 的全部 task-notification 合并成一批**——一个模型轮消费多条通知（CB 的 drainSubagentNotifications 已同构）；
- **flush 时机纪律**：入队即幂等 drain；turn loop 内只有「带新输入的请求前」消费通知——防止 Stop-hook 续跑等重发请求被重复插入通知；
- 流式中的 turn 与队列解耦：新输入走 `steerTurn` 进 pendingInputs，delivery 分 `guide`（inline，下个请求注入）和 `queue`（下一轮）；
- v4 新增：`queueAutoDrain`（held 队列授权位）、`acquireForegroundPromotionLease`（立即发送的原子提升——出队与租约消费同一同步步，防止通知抢先出队）；
- **队列权威双源**：内存 pendingInputs（热态）+ SQLite session_input 表（冷态）。

> CB 对照：CB 的 host-queue（run 结束 FIFO flush + 立即发送=中断当前轮插队）功能面对齐，但没有优先级分层与 promotion lease 的原子性。「立即发送」的竞态（通知抢先出队）值得 CB 借鉴 lease 方案。

## 4. 工具系统：契约 + 执行管线

**契约两层**（v3.17 结构）：
- `contracts` 层 `ToolContractDeclaration`：inputSchema/outputSchema、`permission: ToolPermissionSpec`、`resultBudget`（maxInlineBytes/maxModelBytes/strategy: inline|truncate|artifact）、timeout、cancellation、trace、executionMode；
- core 层 `ToolEntry extends ...`：metadata（readOnly/destructive/concurrentSafe/stopTurnOnSuccess）、handler、**7 个可选生命周期钩子**：
  - `resolveModelContract`（按模型能力投影 schema）、
  - `validateInput`（语义校验）、
  - **`resolveInput`（入参归一化成"将要发生的执行事实"，位置刻意在 PreToolUse hook 前——hook/权限/确认窗/handler 读同一份字节）**、
  - `applyInputAdjustments`（确认窗用户调整）、
  - `formatModelContent`（forModel 双轨）、`resolveTimeoutBudgetMs`、`prepareApproval`（ask 最后一道，只能收窄不能放大）。

**执行管线**（`call-runner.ts`，861 行）：
```
resolveDeferredToolCall → registry lookup（miss 发 <tool_use_error>）→ retainExecution
→ zod runtimeInputSchema 校验（7 种 issue 类型人话错误，含路径）
→ entry.validateInput → entry.resolveInput → PreToolUse hooks（可改输入，改后再校验一次）
→ resolveToolPermission（permission-flow：mode+规则+弹窗）→ applyInputAdjustments
→ ToolCallStarted（副作用旗标先于 handler）→ ToolDeadline 可暂停超时 → handler
→ validateOutput → serializeOutput（resultBudget）→ PostToolUse hooks → createToolResultDisplay
→ ToolCallResult/Error → backgroundTasks.track
```

**结果四轨**（没有 forModel/forUI 字段名，实际是四路）：
1. **forModel**：`formatModelContent` 产出或按 resultBudget.maxModelBytes 截断 → 进 provider 历史；
2. **forUI**：`display: ToolResultDisplayPayload`（按工具名分派：Bash diff hunks≤8、图片≤2 张 200KB...）；
3. **artifact**：strategy=artifact 且超限写 artifactStore，模型只见 `<persisted-output>` 预览；
4. **持久 part**：整批结果**同步**提交进两份历史（防中途失败缺结果）再逐项 persistPart（SQLite part 行）。

**调度**：拓扑排序+并行分组——destructive 不并行、concurrentSafe/readOnly/sideEffectScope=none 可并行，组上限 maxConcurrency=10。

> CB 对照：CB 单轨 `Promise<string>` + 错误串前缀判定 + `__EDIT_DIFF__` 尾巴旁路。**CB 演进建议（P0）**：给 ToolDefinition 加可选 `formatDisplay(result): ToolResultDisplayPayload` 与结构化错误 `{code, message}`，先把「UI 展示」从字符串约定里解放出来；`resolveInput` 一次归一化原则在 CB 加 CreateWorkflow（脚本要被确认窗/引擎/草稿三处读）时是硬前置。

## 5. 上下文压缩：三层 + 熔断（CB 已同构，补细节即可）

| 层 | 触发 | 行为 |
|---|---|---|
| microcompact | token 压力（min(90%阈值, 阈值-2000)）或 60 分钟空闲 | 清旧工具结果：候选=9 个可清工具的可清组，保留最近 5 组，替换 `"[Old tool result content cleared]"`；节省<256 token 放弃；媒体块永不清 |
| auto compact | 阈值 = contextWindow − min(maxOutput,21K) − 13000 | 摘要模型（≤20K 输出）→ CompactBoundary 事件；连续失败 ≥3 熔断 |
| reactive | 仅模型步内 context-exceeded 时 | 每步一次 |

**token 计量**：provider usage 锚点（最近已提交 assistant 的 usage.inputTokens）+ 锚点后 entry 本地增量 = 总数。**rapid-refill 熔断**：压缩后不足 3 个完整工具轮又触发压缩 → 计数；连续 3 次 → auto 直接抛错结束 turn（防压缩死循环）。

> CB 对照：CB 已有 auto-compact（阈值=输入预算−20K、下限 80%）+ microcompact（保留最近 6 条）+ truncateMessages 兜底 + failedAutoCompacts 3 次熔断 + overflowRecovered 溢出恢复。可抄：provider usage 锚点+本地增量计量（CB 的 tokenTracker 只按 API 可见子集统计）、rapid-refill 熔断、60 分钟空闲触发。

## 6. 流式与事件协议

- adapter 产出内部事件：`start/text_start/text_delta/text_end/reasoning_*/tool_input_start/delta/end/tool_call/provider_tool_result/finish/error`；
- 文本 delta 三路消费：累进流式快照（取消时落盘）+ 回调（喂**流式工具执行协调器**——tool_input 完整即可开跑）+ 带背压的事件队列；
- **tool_input_delta 行缓冲策略：遇换行或 4000 字符才 flush**（Write/Edit 打字机体验的流量优化）；
- 结束事件带 usage/stopReason/fileChanges/contextUsageBreakdown；
- 异常恢复链：selectionFallback → stream recovery（6 种事件）→ admission 重试 → context-exceeded 恢复。

> CB 对照：CB 的 50ms 节流三回调 + 宿主 stream.delta 前缀延长判定已同构；可抄「流式工具执行」（参数完整即开跑，省一拍）与 4000 字符行缓冲。

## 7. 子代理

- **生命周期**：`agentHandler` → subagentPort.launch() → 前台/后台判定（前台 Promise.race：执行完成 vs autoBackgroundMs 转后台）→ **child AgentRuntime（独立 sessionId、taskType:"subagent_child"、parentSessionId）→ childRuntime.executeTurn(prompt)——复用同一主循环**；
- **端口借用**：child 不建新连接——MCP 借父的 callTool（connect/disconnect 一律拒绝）；permission broker 与 provider headers 路由回父会话身份；回话走 coordinator port 入父队列；
- **继承矩阵**：继承 modelSelection/streaming/bashTimeout/toolSearch/env（校验 cwd 一致）/dynamicWorkflowEnabled（结构性继承防绕灰度）/toolDisallowlist/全部宿主端口；**不继承**：subagents.enabled=false（child 不再派孙）、Project Context（只带 userInstructions 快照）、permissionService（Explore 用独立只读 PS）；
- **并发闸门**：无独立个数上限，靠①同一父会话的并行子代理**共用一条模型请求准入队列**（防 1302 风暴）、②maxTurns 默认 4、③工具调度 maxConcurrency=10。

> CB 对照：CB 的 runSubAgentLoop（前台/后台+通知注入+steering+续跑）机制面对齐；深度恒 1 与 ZCode child 不派孙同构。可抄：模型请求准入队列（CB 多 spawn 并发时防限流风暴）、权限服务分离（Explore 只读）。

## 8. 会话持久化与 rewind

- **SQLite**（`~/.zcode/cli/db/db.sqlite`）：session/message/part/session_input/session_entry(KV)/session_task_link(父子链)/turn_usage/todo/dwf_* 等表；
- **冷恢复权威不是事件而是 message/part 行**（事件只是 UI 投影源）；hydrate 时重建 read-file state、权限 grant marker、模型选型、工作流激活；
- **rewind 三层**：会话 rewind（事件截断+恢复锚点）/ 工作区 rewind（CheckpointCreated 挂 messageId）/ 文件级 rewind（从 checkpoint snapshotRef 恢复）；另有 session-fork 四种（stable/selection-side/before-input/workspace）。

> CB 对照：CB 的 clerkbox.db + chat-row 编解码 + rewind 三 scope（conversation/workspace/both）完成度高（CB 盘点结论：与 ZCode 差距最小的子系统之一）。可抄：session_task_link 表（CB 子代理 run 不落库，重启即失——这是 CB 持久化最大缺口）。

## 9. 新增一个工具的接线清单（ZCode 8 步 vs CB 12 步）

**ZCode**（以 FillWorkflowHole 为例）：①contracts zod schema → ②handler 拆分（resolve/splice/description 分件）→ ③ToolEntry 组装（7 钩子+permission.alwaysAsk）→ ④注册进 builtInTools+灰度集合 → ⑤tool-allowlist → ⑥executor display 分支 → ⑦UI renderer+i18n+摘要 → ⑧文档。
