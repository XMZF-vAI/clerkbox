# 研究报告 04：权限与安全模式（三种模式怎么实现的）

> 对标对象：ZCode v3.17.1 `core/src/permission/service.ts`、`tool/handlers/{bash-command-parser,guarded/}`,`executor/permission-*.ts`、`packages/ui/PermissionDialog.tsx`
> 调研日期：2026-11-01 · 用途：CB 权限体系升级（用户核心问题：「那三种安全模式分别是怎么实现的？咱们要怎么搞？」）

---

## 0. TL;DR

ZCode 的模式枚举其实是 `plan | build | edit | yolo | guarded | auto` 六个值，但**安全模式下拉里用户可见的是三档**（2026-11-03 实机截图核实）：`build`＝变更前确认（改文件前先问我，**默认**）、`guarded`＝自主模式（在有风险时询问）、`yolo`＝完全访问（减少确认次数）。**`plan` 不在安全模式菜单里**——它是独立的 planEnabled 协作开关（只读出计划），不是安全档位，见 §2 关键结构事实。`edit` 是隐藏的历史兼容值，`auto` 保留未实现。

实现核心就三样：①**每个工具声明安全元数据**（riskLevel/sideEffectScope/needsApproval）；②**一个 fail-closed 判定瀑布**（18 级，第一个命中生效）；③**审批=挂起 Promise + 选项 listbox + 建议规则持久化**。Bash 的精细化靠 unbash AST 解析 + any/every 双语义。CB 已有 fail-closed 宿主引擎和审批 UI 骨架，缺的是「规则化」：持久规则、per-tool 模式、命令前缀规则。

## 1. 模式清单与语义

**定义**：`contracts/src/interfaces/session.port.ts:33`
```ts
export type CollaborationMode = "plan" | "build" | "edit" | "yolo" | "guarded" | "auto";
```

**安全模式下拉**（Composer 输入框旁，实机截图核实三档；`packages/shared/src/zcode-agent-model-state.ts`）：

| 模式 | UI 名称（截图原文） | 语义 |
|---|---|---|
| `build` | 变更前确认 · 改文件前先问我（**默认**） | 只读放行；critical/high 风险 ask；一切有副作用工具 ask；低风险 session 态放行 |
| `guarded` | 自主模式 · 在有风险时询问 | YOLO 基线 + 命中「明确危险命令清单」时**单次审批**（`approvalMode:"user-once"`：禁永久规则/会话授权/Full access/hook 代批） |
| `yolo` | 完全访问 · 减少确认次数 | 直通放行（除 requiresUserInteraction / alwaysAsk / disallowedTools） |

**不在安全下拉里的两个枚举值**：`plan`（只读+非破坏 MCP 放行，**其余一律 deny（不是 ask）**）——**不是安全模式**，是独立的协作开关；`edit`（菜单已隐藏的历史兼容值）；`auto`（保留未实现，一律 deny）。

**关键结构事实**：`plan` 不是 mode 的一个值——运行时是「基础模式 + 独立 planEnabled 开关」（`getMode() => config.mode ?? "build"`；EnterPlanMode/ExitPlanMode 只翻 planEnabled）。`guarded + planEnabled=true` 时 Plan 限制优先，**审批不能解除**。

**切换位置**：Composer 权限下拉（只编辑草稿，随消息提交生效）+ Plan 独立勾选 + `cycleSessionMode` 快捷键；**切入 YOLO 前强制确认弹窗**（风险说明 + "我已了解风险"复选框，每次重新勾选，`docs/ui/yolo-mode-confirmation.md`）；审批弹窗里还有 `fullAccess` 选项（审批中直接升权 yolo + 持久 receipt）。后台任务（OffPeak/Cron）另有一枚举变体，缺省 = yolo。

## 2. 判定引擎：18 级 fail-closed 瀑布

入口：每次工具调用执行前**现读 mode**（call-runner.ts:220——切换即时生效，只影响尚未判定的调用）。核心在 `core/src/permission/service.ts:101-285`，自上而下第一个命中生效：

```
 1. Plan 进出转换工具（EnterPlanMode/ExitPlanMode）allow/deny
 2. requiresUserInteraction → ask（在 disallowedTools 里则 deny）
 3. guarded + 命中危险规则 → ask + approvalMode:"user-once"
 4. alwaysAsk → checkAlwaysAsk（硬阻断 deny 优先 → 会话级 allow → 否则 ask；
    ask 压过 yolo/plan 直通，压不过阻断）
 5. yolo|guarded（非 plan）→ allow          ← fail-open 基线，全表仅此一处
 6. auto → deny（保留未实现）
 7. disallowedTools → deny
 8. 项目规则 deny → deny
 9. 项目规则 ask → ask
10. ReplyToChannel 预批（窄条件六连）
11. planEnabled → 只读非破坏 allow / 其余 DENY
12. 项目规则 allow → allow
13. WebFetch 预批 URL / 14. CronPauseSelf 预批 / 15. workflow 草稿写入预批
16. config.allowedTools → allow
17. edit 模式 → edit+workspace 放行
18. checkBuildMode（fail-closed 兜底）：readOnly 非破坏 allow → critical ask → high ask
    → session+low allow → needsApproval/destructive/sideEffect≠none ask → 其余 allow
```

**未知工具兜底**（`resolveCapability`，service.ts:645）：Read/Glob/Grep 等只读 → low/none；Write/Edit/Bash → high+workspace+needsApproval=true。**不认识的东西最终都 ask——fail-closed 的关键。**

> ⚠ 注意第 5 步在 disallowedTools（第 7 步）之前是 ZCode 的已知历史顺序问题；他们的 alwaysAsk 路径（第 4 步）自己修正了这一点。**CB 实现时应把 disallowedTools 提到 yolo 直通之前。**

**工具安全元数据**（`contracts/src/tools/contract.ts` ToolPermissionSpec）：
```ts
permission: string; riskLevel: low|medium|high|critical;
sideEffectScope: none|session|workspace|network|userInteraction;
needsApproval: boolean; alwaysAsk?: boolean; denyPriority?: ...; patternSources?: ...
```

## 3. Bash 精细化：unbash AST + any/every 双语义

- **unbash 是外部 npm 包**（v4.0.1，纯 POSIX shell 语法解析器）；包装层 `bash-command-parser.ts` 产出 `{commands[], hasParseErrors, hasDynamicWords, hasUnsupportedSyntax}`。
- **动态性检测**：变量展开/命令替换/进程替换/算术展开一律 `hasDynamicWords=true`——**权限判定不能把展开当 argv**。
- `isBashCommandPermissionSafe = !parseErrors && !unsupported && !dynamic`——不安全则**前缀规则整体不可用，退回整条命令精确匹配**（fail-closed）。
- **any/every 语义**（`bash-command-rule-evaluator.ts`）：
  ```
  allow：subjectGroups.every(group => group.some(命中))   ← every：命令行里每条非只读 invocation 都要被规则覆盖
  deny/ask：subjectGroups.some(命中)                       ← any：任一 invocation 命中即触发
  ```
  （`git add . && rm -rf /` 一条 allow 规则放不住——因为 rm 那段没被覆盖。）
- **稳定前缀规则生成**（审批「总是允许」的建议规则，`bash-command-permission-policy.ts:142`）：剥 sudo/env/nohup 包装 → 高危根命令（rm/chmod/dd/mkfs...）**永不生成前缀**只给精确规则 → 其余沿生成的命令树（bash-command-registry.ts）跳过已知选项吞子命令 → 前缀至少 2 token → `prefix:*` 规则（最多 5 条，超出退回精确规则）。

## 4. 审批链路与 UI

```
ask 决议 → PermissionBrokerPort（ManualPermissionBroker：pending Map<requestId,{resolve,reject}>，
          支持 abort/timeoutMs/迟到应答竞速）→ run 在 await 上挂起
       → 协议化 interactionRequestPermission {input, reason, riskLevel, options, origin} → UI
用户点选项 → {decision: allow|deny|modify|escalate, permissionUpdates?, inputAdjustments?}
       → deny → 固定文案回模型（"The user doesn't want to proceed... STOP and wait"，防重试）
       → modify → 重新备输入重判（防"批准 A 跑 B"）
       → allow + permissionUpdates → 规则落盘（失败则工具失败："用户选的始终允许没记住，不能当什么都没发生"）
```

**UI**（`PermissionDialog.tsx`，1121 行，详见报告 01 §5）：模态 + numbered listbox（允许一次/项目始终允许/会话始终允许/拒绝/反馈）+ **复用工具 renderer 渲染预览**（审批窗看到的就是执行后卡片的样子）+ `origin` 徽标（哪个子代理在问）。

**选项收窄策略**（`optionsPolicy`）：`"no-always-allow"` 砍掉持久规则——用于「每次调用内容都不同的工具」（如 CreateWorkflow 脚本，"always allow" 等于永久拆掉闸门）；guarded 的 user-once 只留 allow_once+deny。

## 5. 危险命令识别（guarded 的核心）

`core/src/tool/handlers/guarded/`（705 行）——`matchDangerousCommand(command, dialect)`，dialect ∈ posix/cmd/git-bash；**解析不了 → 不匹配（沿 yolo 执行），明示「不承诺未知语法安全」**。命中返回精确字符区间供 UI 高亮。

| 规则 ID | AST 特征 |
|---|---|
| `remove-critical-path` | rm 带 `-r/-R/--recursive` **或** ≥2 个目标 **或** 未引用 glob；`--help/-i` 不抵消危险证据 |
| `git-reset-hard` | `git reset --hard`（soft/mixed/merge/keep 反证） |
| `git-push-force` | `-f/--force/--force-with-lease/--mirror`、refspec `+` 前缀；dry-run 豁免 |
| `git-clean-force` / `git-discard-tree` / `git-stash-clear` / `git-worktree-force-remove` | 对应 git 破坏族 |
| `find-delete` | POSIX find `-delete` |
| `cmd-remove-tree` / `cmd-delete-files` | CMD `rd /s`、`del`（专用 lexer 处理 caret/引号/`%var%`） |
| `robocopy-delete` | `/MIR //PURGE`；`/L` 列举豁免 |
| `rsync-delete` | `--delete*` 家族非 dry-run |
| `system-storage` | dd/mount/umount/mkfs.* |

**接线**：仅当 `mode === "guarded"` 时执行匹配（bash.ts:117）→ 命中即 `{userApprovalRule: ruleId}` → service 第 3 步转 user-once ask。**仅扩展识别层，不动审批核心。**

**沙箱现状（重要事实，2026-11-03 源码复核）**：OS 级 bash 沙箱已撤除——执行适配器注释原话「sandbox 撤除后准备阶段只剩 shell snapshot / capability probe」（`adapters/src/exec/node-execution-adapter-run.ts:399`）。契约层的 `ExecutionSandboxPolicy`（`execution.port.ts:108`，含 `dangerouslyDisableSandbox`）与 `sandbox_violation` 失败类型仍在，但**全仓无任何实现方/消费方**，是死类型；bash 工具描述里「dangerously override sandbox mode」参数文案（`contracts/src/tools/bash.ts:68`）只剩遥测。——**安全边界完全靠权限模式+审批**。路径越界也**故意不硬拦**工作区外（注释：子代理可能要读用户指定的兄弟仓库）；实际边界靠 memory 目录限定、WebFetch 出网护栏、bash cwd 策略。注意：dynamic-workflow 文档里的 "sandbox" 指**进程隔离**（子进程 vm + NDJSON facade 桥），不是安全沙箱，边界仍是脚本确认门。

## 6. 子代理与运行时效果

- **继承规则一行**：`inheritPermissionMode(parent, child) = parent==="guarded" && child==="yolo" ? "guarded" : child`——父 guarded 会把子的 yolo/dontAsk/bypassPermissions 收紧为 guarded。
- **审批路由回父会话**：子代理共用父 permissionBroker，请求带 `{agentType, childSessionId, parentToolCallId}` origin → UI 徽标显示「哪个子代理在问」。
- **workflow actor**：模式在建 run 那刻定死记入 journal；会话换模式不影响在飞 run。
- **切换的运行时效果**：mode 每次调用现读 → 只影响尚未判定的调用；已授权不回收；切换时**先持久化再改内存**（"保存失败不发布成功快照"）+ SessionModeChanged 事件。
- **持久化分层**：项目规则（allow/deny/ask）→ SQLite per-project；项目默认模式 → local_setting；群聊会话模式 → session 行内（防污染项目默认）；会话内"总是允许"记忆 → **纯内存**（重启/新会话即失）；OffPeak/Cron 模式 → 任务行。

## 7. CB 现状与差距

CB 已有：fail-closed 宿主引擎（无窗口即拒、120s 超时即拒、grantKey 会话放行集合、settlePermission 唯一收尾）、三档 approvalMode（manual/auto/full）、危险命令正则库（40+ 模式）、PermissionCard 编号三选项 listbox、审计留痕、远程禁批。

**缺口**：
1. 无持久权限规则（allow/deny 列表、命令前缀规则）——放行集合重启即失；
2. 无 per-tool 模式语义（build/guarded/yolo 三档安全模式对应的瀑布不存在——CB 是全局 approvalMode 而非 per-call 判定）;
3. 危险命令是正则而非 AST（40+ 正则 vs unbash AST + any/every）;
4. 无 guarded 式「危险命令单次审批」语义;
5. 无「总是允许」建议规则生成（稳定前缀）;
6. 审批预览不复用工具 renderer。

## 8. CB 落地方案（直接回答「咱们要怎么搞」）

### 第一期：安全三档（build / guarded / yolo——先复刻截图里的下拉；plan 是独立开关不在这期）
1. **数据结构**（对齐 ZCode 命名便于将来升级）：
   ```ts
   type SecurityMode = "build" | "guarded" | "yolo";   // CB 现有 manual/auto/full 与三档一一对应，先核对语义再重命名
   type CollaborationMode = SecurityMode | "plan";      // plan 是独立的 planEnabled 开关，不进安全下拉
   // 每个工具注册时声明 ToolPermissionSpec（CB 的 tool-registry.ts 定义处加字段）
   ```
2. **判定引擎**（一个纯函数，照抄瀑布裁剪版，放进 CB 的 `checkToolPermission` 演进）：
   ```
   build:   readOnly → allow；critical/high → ask；needsApproval||destructive||sideEffect≠none → ask；else allow
   guarded: yolo 基线；命中危险命令清单 → ask + user-once（二期细化）
   yolo:    disallowedTools → deny；requiresUserInteraction → ask；else allow
   公共前置（三档都先走）：项目 deny → deny；项目 ask → ask；项目 allow → allow
   ```
   独立于三档的 **plan 开关**（planEnabled）：开 → 只读+非破坏 MCP allow，其余 DENY（不是 ask）；guarded + plan 同开时 Plan 限制优先、审批不能解除。
3. **审批链路**：CB 的 PermissionCard 已是骨架；补「本项目始终允许」选项 → 建议规则先做两 subject（精确命令 / file_path），稳定前缀二期；
4. **持久化**：项目规则一张 JSON 列（version+allow/deny/ask）进 clerkbox.db；项目默认模式一行；会话记忆只进内存 Map（现状保留）。

### 第二期：guarded（差异化亮点）
5. **AST 化**：引 `unbash`（MIT，纯 POSIX）替换 40+ 正则；包 `analyzeCommand → {invocations, safe}`；`safe=false` 时 allow 规则一律不命中、退精确匹配；
6. **any/every 双语义**判定器；
7. **危险清单先做六条**：`rm -r/-R/--recursive 或≥2目标或裸glob`、`git reset --hard`、`git push -f/--force-with-lease/--mirror/+refspec`、`git clean -f`、`find -delete`、`rsync --delete*`——全部 AST 判定，`-h/--help`/`--dry-run` 豁免；
8. **user-once 约束**：该次审批不提供"总是允许"、不写规则、不可升权——实现上就是 `approvalMode` 字段过滤选项列表。

### 第三期：子代理
9. 继承一行 + 审批请求带 `{agentName, parentToolCallId}` origin 徽标（CB 的 subagent-control 注册表已有坐标）。

### 明确不抄的
- OS 级沙箱（ZCode 自己都撤了）；工作区外路径硬拦（ZCode 故意不拦）；`edit`/`auto` 两模式。
